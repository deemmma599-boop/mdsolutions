the definition

What are Core Web Vitals?

Core Web Vitals are three specific metrics Google uses to quantify real user experience on a web page. They are not lab simulations and not vanity speed scores — they are measured from actual Chrome sessions across thousands of real devices, networks and locations, aggregated at the 75th percentile[reference:0]. In other words: they reflect what most of your visitors actually experience, not what a fast machine on a fast connection sees.

The three metrics cover three distinct dimensions of experience. Largest Contentful Paint (LCP) measures loading speed — when the largest visible element (usually a hero image or main heading) finishes rendering. Interaction to Next Paint (INP) measures responsiveness — how quickly the page visually responds after a click, tap or key press. Cumulative Layout Shift (CLS) measures visual stability — how much visible content moves unexpectedly during loading[reference:1].

Together they form the page experience layer of Google's ranking systems. They do not replace content relevance or authority — but when two pages compete for the same query with comparable content, the one delivering better Core Web Vitals consistently earns the higher position[reference:2]. Poor performance also hurts indirectly: slower pages increase bounce rates, reduce engagement and consume more crawl budget[reference:3].

The practical implication is straightforward: Core Web Vitals are simultaneously a user experience problem and an SEO problem. Fixing them improves both at once — which is why they sit at the centre of any serious performance programme.

At a glance

  • LCP: loading speed — good at ≤ 2.5 s.
  • INP: responsiveness — good at ≤ 200 ms.
  • CLS: visual stability — good at ≤ 0.1.
  • Measured: 75th percentile of real Chrome users (field data).
  • Ranking role: a tiebreaker within page experience — not a replacement for content quality.
the three metrics

LCP, INP and CLS — thresholds and fixes

Each metric has a clear "Good" threshold, a diagnosis method and a known set of fixes. Here is what each one measures and what typically moves it.

LCP — Largest Contentful Paint

Loading speed: when the largest visible element renders.

Good ≤ 2.5 s Needs improvement 2.5–4.0 s Poor > 4.0 s

LCP is the hardest Core Web Vital to pass — only around 62% of mobile pages meet the threshold — and it is the most common failure point for enterprise homepages[reference:4][reference:5]. It breaks down into four subparts: Time to First Byte (TTFB), resource load delay, resource load time and element render delay[reference:6].

  • Compress and convert hero images to WebP or AVIF; add fetchpriority="high" and preload the LCP element.
  • Reduce server response time (TTFB) with caching and a CDN.
  • Eliminate render-blocking CSS and JavaScript; inline critical CSS.
  • Use font-display: swap and preload key fonts.

INP — Interaction to Next Paint

Responsiveness: visual latency after every interaction.

Good ≤ 200 ms Needs improvement 200–500 ms Poor > 500 ms

INP replaced First Input Delay (FID) as the interactivity metric on 12 March 2024[reference:7]. FID only measured the delay before the first interaction was processed; INP measures the full latency of all interactions across the page's lifetime — a far more demanding and representative measure[reference:8]. It is caused by long JavaScript tasks blocking the main thread, heavy event handlers and excessive DOM size[reference:9].

  • Break long JavaScript tasks into smaller chunks (under 50 ms).
  • Debounce and throttle event handlers; defer non-critical scripts.
  • Reduce DOM size (over 1,500 elements is a warning sign).
  • Audit and defer third-party scripts (analytics, chat, A/B testing).

CLS — Cumulative Layout Shift

Visual stability: unexpected movement of visible content.

Good ≤ 0.1 Needs improvement 0.1–0.25 Poor > 0.25

CLS quantifies how much visible content jumps around during and after load. Every unexpected shift — an image loading without dimensions, a font swapping late, an ad injecting above existing content — frustrates users and can cause accidental clicks[reference:10]. It is the most straightforward of the three to fix, and the most commonly passed (around 81% of pages)[reference:11].

  • Always set explicit width and height (or aspect ratio) on images and videos.
  • Reserve space for ads, embeds and dynamic content containers.
  • Use font preloading and font-display: optional or swap with matched metrics.
  • Never insert content above existing content unless triggered by user interaction.

Leaner, cheaper infrastructure

how it is measured

Field data vs lab data — and why the difference matters

Core Web Vitals are measured in two fundamentally different ways. Confusing them is the most common reason teams "fix" performance and see no ranking change.

Field data (real users)

What Google actually uses for ranking.

  • Source: Chrome User Experience Report (CrUX) — aggregated from real Chrome sessions.
  • Access via: PageSpeed Insights, Search Console Core Web Vitals report, CrUX API, or custom Real User Monitoring (RUM).
  • What it tells you: what your actual visitors experience across their devices, networks and locations.
  • Percentile: 75th percentile — 75% of page loads must meet the "Good" threshold for the page to pass.
Field data is the ground truth for ranking. Always baseline it first, and re-check it after changes have had time to propagate (typically 28 days).

Lab data (simulated)

What you use for diagnosis and debugging.

  • Source: Lighthouse, Chrome DevTools, WebPageTest — controlled conditions.
  • What it tells you: what is technically possible, and which specific resources or scripts are causing problems.
  • Limitation: lab conditions cannot replicate real-device diversity, cache state or actual interaction patterns[reference:19].
  • Best use: reproducible diagnostics, regression testing after deploys, and identifying the cause behind a field failure.
A page can score 100 in Lighthouse and still fail Core Web Vitals in the field — and vice versa. Use lab data to fix, field data to judge.

what usually goes wrong

The bottlenecks we see most often

Across audits, the same handful of issues account for the majority of Core Web Vitals failures. Most are fixable without a rebuild.

Unoptimised hero images

Large, uncompressed JPEGs and PNGs as the LCP element — often several megabytes. Fix: modern formats, correct sizing, compression and priority hints[reference:20].

Render-blocking CSS and JS

Stylesheets and scripts in the head that delay first paint. Fix: critical CSS inlining, deferring non-critical scripts, and removing unused code[reference:21].

Slow server response

TTFB above 200–800 ms delays everything that follows. Fix: server caching, edge CDN, database query optimisation and faster hosting[reference:22].

Third-party script bloat

Analytics, chat widgets, tag managers and A/B testing tools competing for main-thread time. Fix: audit, defer, consolidate and remove what is not earning its cost[reference:23].

Long JavaScript tasks

Heavy framework hydration and large bundles blocking the main thread, making every interaction feel sluggish. Fix: code splitting, task breaking and lighter hydration[reference:24].

Layout shifts from dynamic content

Images without dimensions, late-loading fonts, injected ads and cookie banners pushing content down. Fix: reserved space and stable font loading[reference:25].

Core Web Vitals questions, answered

What are Core Web Vitals?

Core Web Vitals are three specific metrics Google uses to measure real user experience on a web page: Largest Contentful Paint (LCP) for loading speed, Interaction to Next Paint (INP) for responsiveness, and Cumulative Layout Shift (CLS) for visual stability. Each is assessed at the 75th percentile of real Chrome user data.

What are the Core Web Vitals thresholds?

For a "Good" rating: LCP must be 2.5 seconds or less, INP must be 200 milliseconds or less, and CLS must be 0.1 or less. "Needs Improvement" ranges are LCP 2.5–4.0 s, INP 200–500 ms and CLS 0.1–0.25. "Poor" is LCP above 4.0 s, INP above 500 ms and CLS above 0.25.

Do Core Web Vitals directly affect Google rankings?

Core Web Vitals are a confirmed ranking signal within Google's page experience system, but they are best understood as a tiebreaker: they matter most when competing pages have similar content relevance and authority. Poor Core Web Vitals also indirectly hurt rankings by increasing bounce rates, reducing engagement and wasting crawl budget.

What is the difference between field data and lab data?

Field data comes from real users (Chrome User Experience Report / CrUX) and is what Google uses for ranking. Lab data comes from controlled tools like Lighthouse and is used for debugging. A page can score well in Lighthouse but still fail Core Web Vitals in the field because of real-device conditions, third-party scripts and network variability.

How long does Core Web Vitals optimisation take?

Most optimisation projects take 2 to 6 weeks depending on the size of the site and the severity of the issues. Quick wins such as image compression and render-blocking fixes can show results within days; deeper work such as JavaScript refactoring and server architecture improvements takes longer.

What is a good LCP score?

A good LCP is 2.5 seconds or less at the 75th percentile. LCP is typically the hardest Core Web Vital to pass — only around 62% of mobile pages meet the threshold — and it is usually caused by slow server response, unoptimised hero images, render-blocking resources or late-discovered LCP elements.

What replaced First Input Delay (FID)?

Interaction to Next Paint (INP) replaced First Input Delay (FID) as the responsiveness Core Web Vital on 12 March 2024. FID only measured the delay before the first interaction was processed; INP measures the full latency of all interactions across the page's lifetime, making it a more demanding and more representative metric.

Can you improve Core Web Vitals without rebuilding my site?

In most cases, yes. The majority of Core Web Vitals issues are fixable through targeted changes: image compression and modern formats, font loading strategy, deferring non-critical JavaScript, reserving space for dynamic content, improving server response and adding caching or a CDN. A full rebuild is rarely required.
